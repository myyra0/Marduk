# Filesystem support and proof matrix

**Status:** Planned targets, not runtime results. Filesystem support is an **OS/driver + filesystem + mount configuration + role + deployment method** claim, not a list of file extensions or mount names. See [deployment research](deployment.md) for private-view options and [M1-R03](../contracts/m1-native-proof.md) for durability proof.

**The proof matrix is not a product-wide filesystem allowlist.** The pinned reference does not generally require ext4 or any other filesystem name: it attempts the transfer, has scoped link fallbacks, and shows an advisory for some Linux-mounted NTFS and FAT-family targets. Marduk should follow the broader approach—shared OS operations and capability checks, not one deployment engine per filesystem—while separating "this operation is available" from "this configuration has a supported crash-recovery guarantee." No filesystem is dropped just because it is not in the first proof set; an unmet safety precondition still blocks the affected write.

## What we plan to support

| Setup | Intended support | Important boundary |
|---|---|---|
| Linux local ext4 | M1 copy deploy/restore and local managed storage. Test physical link modes separately in M2 and private view later. | Prove no-clobber create, safe replacement, restore, root identity and file/namespace persistence in the named setup. |
| Linux local Btrfs | **Same M1 copy and recovery target as ext4**, not an optional filesystem for the new product. Test normal same-subvolume use and separate library/game subvolumes. | Two subvolumes on the same disk can reject hardlinks and file rename across them. Stage the final write in the destination's subvolume, not just on the same drive. Btrfs file identity includes a subvolume discriminator; inode alone is not unique. |
| Windows local NTFS | M1 copy deploy/restore and local managed storage using the native Windows adapter. Test later link/view modes on their own. | NTFS hardlinks stay on one volume; symlinks can depend on privileges and game behavior. Windows file/namespace durability needs its own evidence. |
| NTFS mounted on Linux | Planned qualification in `M2-D03`, not automatically covered by native Windows NTFS. Probe kernel `ntfs3` first, then treat `ntfs-3g` as a separate driver. | Record driver, mount options, writable state, identity, filename/attribute behavior and link/durability results. Do not force writes on an unusable or dirty volume. |
| XFS and other local filesystems | Design to work by qualifying the needed capabilities rather than hard-coding the product to ext4, Btrfs, and NTFS. Not included in the first verified matrix. | Add representative tests before advertising target support or recovery. Refuse unsafe mutations without implying the filesystem cannot be read or will never be supported. |
| FAT/exFAT, network or removable storage | An available, readable archive can be imported to a verified local library without modifying the source. Writable game roots or libraries on these setups need separate qualification. | Reading imported bytes does not imply durable rename/locking, reliable root continuity or link support. Do not claim network/share or removable-device recovery from local-disk tests. |

Different roles can live in different places. A mod archive can be read from one drive and copied to private local storage. A game can also be on a different verified volume or Btrfs subvolume from that library. **Copying bytes between the two is fine; final publication into the game uses a temporary file in the target's own rename domain.** A journal tracks the result rather than pretending a database write and a game-file move on two volumes are atomic.

## General strategy

- Use one Linux implementation for common native effects. Teach its capability and identity checks about subvolumes, mount boundaries and driver-specific behavior where needed, rather than adding a whole deployment engine per filesystem.
- Discover capabilities per source/target relationship and resolve the requested method before mutating. Real mount permissions, backup metadata and crash behavior still gate production writes; a successful probe of `rename` or `link` is not a durability guarantee.
- Physical copies remain the broadest candidate. Hardlinks are conditional on the actual link domain; symlinks on permissions, path visibility, and game/tool compatibility. A private view also needs the selected launcher/backend to work. If a requested mode is unavailable, explain why and let the user select another supported mode. Never silently switch a clean private view to a physical deployment.
- Btrfs snapshots and reflinks are potential tools or optimizations, **not** transaction backups or prerequisites for Btrfs support. A subvolume snapshot does not cover nested subvolumes and cannot automatically roll back a journal and a game on different roots.
- The pinned reference's filesystem detector, deploy advisory and transfer fallback are in `src/Utils/fs_check.py`, `src/Utils/deployment/pipeline.py:702–775` and `src/Utils/deployment/shared.py:1083`. These establish a relevant workflow, not a tested crash guarantee. If a supported-use case cannot meet the new safety contract, bring the scope decision to the user rather than treating the old warning as proof or silently dropping it.
