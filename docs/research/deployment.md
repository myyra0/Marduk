# Deployment research: legacy behavior and Windows options

**Scope:** Source inspection only. The pinned legacy tree establishes behavior. MO2 is consulted only for native Windows mechanisms and their implications. No deploy, game launch, package build, or crash test was run.

## What the legacy code does

| Behavior | Pinned source and implications |
|---|---|
| Physical placement | `src/Utils/deployment/shared.py:663,1083` defines hardlink, symlink and copy. The transfer helper tries symlink after particular hardlink capability errors, then copy; explicit symlink has its own error filter. Not all failures should be interpreted as missing capabilities: `deployment/_selftest.py` specifically treats disk-full and transfer failures as fatal. |
| Deploy and restore | `deployment/pipeline.py:702,1287,1434` checks mount/paths, consults handler policy, applies the file plan and adapter side effects, commits filegraph state only on success, and records failure/recovery. Restore re-discovers the prior deployed profile and recorded paths rather than trusting currently selected settings, also handling a missing installation and root artifacts. |
| Private Linux view | `vfs/overlay.py:1,434,1397,2462` says the default is **a materialized shadow tree**, using hardlink/symlink/copy placement, then a process-private bind mount through bubblewrap. For some UMU/Steam Runtime routes it runs from the shadow path directly to avoid nested namespace problems; not every native game tolerates relocation. Kernel/FUSE overlay routes are older manifest/diagnostic alternatives, not the default design to reproduce. |
| Hybrid deployment | `vfs/_builtin_phase1_selftest.py` includes standard physical and private-view coexistence and RE Engine invalidation hybrid rollback. Root-folder, custom destination and external-loader paths can still require writes outside a game view. A label like “VFS” cannot imply zero writes everywhere. |
| Pending views and captured output | `vfs/overlay.py:1460,2781` writes a pending marker before side effects, preserves retry visibility through cleanup, and distinguishes incomplete view output from a finalized view. Runtime output can be captured into profile storage; editing a hardlinked source in place is still a separate risk, not made safe by naming the directory a shadow. |
| Conflict indexing | The native Rust filegraph has catalog, graph snapshots, incremental calculation and operation records. Its `Cargo.toml` declares `GPL-3.0-or-later` and PyO3; its existing crate is not a drop-in domain dependency. `src/Utils/filegraph` is the application adapter. Keep the option to reuse proven algorithms with confirmed license and isolated adapters. |

`deployment/` and `vfs/` in the table are below `src/Utils/`. Use the deployment, VFS, archive and game-family selftests as candidate behavioral oracles; finding their assertions does not establish that they pass. Re-derive fixtures in isolated synthetic roots, not on a user's installed game.

## Windows research

| Mechanism | What it buys | What must not be promised yet |
|---|---|---|
| Copy | Works across volumes without link creation privilege; deployed writes do not alias mod library bytes. | Uses more I/O and space, requires target write access, and changes the actual game folder. Recovery relies on durable backups and verified replacement semantics. |
| NTFS hardlink | Fast placement without another copy for same-volume regular files. | Two names refer to one file: in-place edits propagate. Do not link the immutable library directly into a writable game/tool view. An isolated disposable source and an explicit mutable-output policy are required. |
| File symlink | Can decouple mod storage and target volume. | Creation without elevation can depend on Developer Mode, and game/tool behavior and target availability vary. Writes through the link still reach its target. Directory junctions are reparse points, not a replacement for per-file merged views. |
| Full private shadow tree launched at a different path | No process interception required; a relocatable game can run against a materialized profile view while original game files are left alone. | Does not preserve canonical installation paths for every game, DRM, launcher or tool. Prove each claimed route and isolation of mutable content. |
| Copy-on-write file clones | Same user-visible result as copy while avoiding eager duplication where the target filesystem supports independent clones. Does not expose mutable library bytes through an alias. | A copy optimization, not a VFS or substitute for the journal. Treat as optional after selecting concrete platform support and measuring material benefit. |
| ProjFS or WinFsp-backed tree | Can avoid eagerly materializing a distinct view; useful only if relocated title/tool compatibility is already proven and building a complete tree is the measured problem. | ProjFS requires a designated projection root and an optional Windows feature. WinFsp supplies a mounted filesystem. Neither by itself gives selected processes a different view of an existing canonical install path. Do not add their operational complexity up front. |
| MO2 USVFS | Selectively presents virtual files and directories to participating native Windows processes while the real installation path stays unchanged. MO2 wires it to process launch and tracking rather than treating it as an installation file-copy switch. | Upstream GPLv3; process architecture, launch paths, child processes, root DLL timing, tool output and compatibility restrictions need proof. Its presence in MO2 is not proof it should be shipped in Marduk. Do not bypass application protections or claim compatibility without a sanctioned route. |

## Linux private-view candidates

“Private game view” is a user-facing mode; **shadow tree**, **kernel OverlayFS**, and **fuse-overlayfs** are backend candidates for it. Physical copy, hardlink and symlink remain separate user choices on supported configurations.

| Linux backend | Better for | Trade-off |
|---|---|---|
| Materialized shadow tree, bind mount where possible and direct launch where valid | Broad baseline: normal filesystem reads, predictable winning files, and a direct-launch route for compatible games when nested runtime namespaces are a problem | Upfront walk and placement, potentially many metadata writes or a large copy; private original-path binding still needs namespace access. Writable files must not share unsafe links with original or immutable payload. |
| Kernel OverlayFS | A lower-cost view for many files, with on-demand copy-up and low per-lookup overhead after mounting | Upper/work filesystem constraints, namespace and distribution policy, mount lifetime, whiteouts, and runtime namespace inheritance. The availability of `bwrap` alone proves none of those. |
| `fuse-overlayfs` | A secondary candidate where kernel OverlayFS cannot serve a proven workflow and FUSE is usable; still gives a merged, writable view rather than copying everything up front | `/dev/fuse` and helper availability, sandbox/host integration, stale mount cleanup and userspace lookup costs. It does not solve Proton/UMU path and namespace routing on its own. Confirm version/backend behavior instead of relying on an upstream default branch. |
| Global mount over the live game root, or a new Marduk filesystem implementation | No demonstrated advantage for parity | Changes what unrelated programs see or requires building and maintaining a filesystem. Reject for this scope. |

**Decision for the design:** use a materialized shadow tree first for Linux private-view parity. Keep kernel OverlayFS as the first challenger if shadow build time or disk use misses the agreed target; consider `fuse-overlayfs` only for a demonstrated compatibility gap where it wins after packaging and launcher checks. Do not expose three backend toggles up front. Keep the deployment method user-selectable, show why a mode is unavailable, and never switch a requested private view to a physical deployment without explicit approval.

**What would change the design:** run the same synthetic profile and output-capture oracle through the shadow backend and any justified challenger. Check warm/cold build time, disk consumed, file-open workload, one native bind route, an actual Proton/UMU route, sandbox/helper availability, outside-process vanilla view, edits to existing files, deletes, generated files and interrupted cleanup. A faster mount is not a win if game/tools can't see it or recovery loses output. See the pinned reference's `overlay.py` (especially `bubblewrap_status`, `fuse_overlay_status`, and `wrap_command`), [Linux OverlayFS](https://docs.kernel.org/filesystems/overlayfs.html), [fuse-overlayfs](https://github.com/containers/fuse-overlayfs/blob/main/README.md), [bubblewrap](https://github.com/containers/bubblewrap/blob/main/README.md), and [UMU](https://github.com/Open-Wine-Components/umu-launcher/blob/main/README.md). Upstream helper repos were inspected with the GitHub MCP.

## Durability findings

- [Microsoft `ReplaceFileW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) requires the files involved to be on one volume, reports specific partial outcomes, and documents that `REPLACEFILE_WRITE_THROUGH` is unsupported. Don't build a recovery guarantee around that flag. The Windows proof must check the chosen publish primitive, file/namespace persistence, ACLs and named-stream policy, sharing failures, and error-state path identities on NTFS.
- [Linux OverlayFS](https://docs.kernel.org/filesystems/overlayfs.html) has explicit copy-up and persistence semantics. A fast view and a durable write are different properties. A successful layer/mount operation does not imply that a modification has reached stable storage.
- [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous) and [multi-file behavior](https://www.sqlite.org/tempfiles.html) distinguish a durable SQLite commit from a transaction across files. An SQLite transaction cannot itself protect game files, mount state, or a remote service. Put the operation journal ahead of external mutations and reconcile the outputs on restart.

## Proposed direction and decision gates

1. Start M1 with safe physical copies and a journal; prove recovery on local Linux and Windows before introducing placement optimizations. Plan on a loose-file-only Skyrim Special Edition fixture: the same title works as a target for native Windows and Linux/Proton research, the pinned handler defines the executables and conventional `Data` layout, and later game-plugin and private-view work can extend it. This is a deliberate first-slice method, not a claim that the reference offers Copy for that game or that copying meets every Skyrim workflow. Do not require Steam, credentials, proprietary assets, LOOT or a real game launch for automated M1 tests. A real smoke is separate and must confirm the chosen route.
2. Keep deployment modes user-selectable. Copy is the M1 baseline, not a global recommendation for the finished product. Offer a recommendation per game and configuration. Plan Linux private-view parity around the shadow-view outcome, not every historical backend or manifest. On Windows, use materialized relocation where a title and its tools can be launched safely from a different path. If a retained private-view workflow needs its canonical path, evaluate reusing USVFS for that specific route.
3. A Windows parity release needs evidence for the retained supported private-view workflows, not necessarily the same backend or blanket coverage for all titles. Physical deployment can stand alone in an explicitly scoped interim release; it is not an invisible fallback for a request that promises a clean install. The user approved keeping GPL-compatible reuse open. Confirm project distribution licensing and compatibility for a specific artifact before integrating or shipping filegraph, USVFS or any helper.
