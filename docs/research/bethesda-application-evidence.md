# Bethesda application and tool effects

**Evidence:** Pinned [application source](../inventory.md). Paths in citations are relative to `src/` unless otherwise stated. This traces nine application families and 55 title/action attachments already counted in the [wizard ledger](wizard-action-ledger.md), plus a Play route and the separately counted game-path registration action. It does not add handlers or prove runtime compatibility. File selectors are not downloaded artifacts. Witnesses are proposed, not frozen.

## CAO and EasyNPC Next

- **CAO acquisition and preparation (M4-Y03/M3-S02):** `wizards_qt/cao_view.py:22–27,48–78,118–150` binds Nexus `skyrimspecialedition` mod `23316`, file `400106` for automatic acquisition; manual instructions ask for the 64-bit archive and separate keyword scan/Browse is not a version pin. `Utils/bethesda/cao.py:14–28,68–94` probes `Applications/Cathedral Assets Optimizer/Cathedral_Assets_Optimizer.exe`; selects `SSE` versus `FO4`, requires that profile directory, seeds missing FO4 settings from SSE if present, writes `General.userPath` in its settings and `General.profile` in shared `profiles/common.ini`. The selected mod is from effective staging, enabled or disabled, without requiring Deploy (`wizards_qt/cao_view.py:80–85,152–212`). After picking runner/prefix the worker rechecks directory presence, maps it through the tool prefix, writes both settings, and starts one interactive process (`wizards_qt/cao_view.py:219–292`). Pinned CAO edits the mod folder in place; the close result reports possible retained changes even after nonzero exit, without checking actual changes (`wizards_qt/cao_view.py:296–319`).
- **CAO witness — `cao_review_binds_both_settings_and_the_writable_mod`:** two same-named mods in different staging roots, disabled member, shared membership, SSE vs FO4 settings, missing profile folder, failure on the second settings write, and cancellation after a verified write. Preserve unrelated INI bytes and the existing mod on failed preparation. Give the tool a checked work copy or qualify recoverable in-place writes; don't infer that a staged folder is safe to mutate when a hardlinked deployment or another profile uses it. Review any replacement and verify resulting files separately from process exit.
- **EasyNPC Next acquisition (M4-Y03/M3-S02):** `Utils/wizards/easynpc.py:9–12,83–119` selects `skyrimspecialedition` mod `187138`; for Premium it filters category ID `1` or category label `MAIN` and maximizes `(uploaded_timestamp, file_id)`. The manual scanner checks all effective download locations, excludes Verify and Post-Build names, and uses `EasyNPC Next`/`EasyNPC-Next` or the standalone mod-ID token to find a nonempty candidate. `wizards_qt/easynpc_view.py:57–109,127–156,172–192` arms a freshness cutoff for the watcher, offers manual rescan/Browse and expects `Applications/EasyNPC Next/EasyNPC.exe`. The shared acquisition worker distinguishes exact metadata matching from a stable-size fallback (`Utils/downloads/mpi.py:72–166`). The desktop's fetch-start guard is not reset by its Get Latest button in this view, so a repeat click is not proof of a new lookup. The shared extractor can merge into an existing Applications directory; an executable already there is not proof of a successful upgrade (`wizards_qt/_view_base.py:505–574`). `easynpc_main_identity_survives_retry_and_manual_choice`: use Main ties, newer optional files, a recently cached Verify decoy and incomplete/manual archives; keep the selected exact file and verified previous app across retries, and honor late cancellation.
- **EasyNPC Next run and output (M4-Y03/M2-L01/M3-X03):** `wizards_qt/easynpc_view.py:194–216,218–280,287–357` requires a successful Deploy callback and compares the active profile name before launch. In the selected Wine prefix it checks x64 VC++ and .NET 8 Desktop, then requires per-executable Windows 7 compatibility setup (`Utils/wizards/easynpc.py:66–80`). The pinned .NET download targets x64 `8.0.25` (`Utils/wine/proton.py:24–34,121–149`); VC++ uses the rolling Microsoft x64 installer and prefix detection at minimum `14.30` (`Utils/wine/health.py:59–60`, `Utils/wine/protontricks.py:124–148,760–788,890–969`). Install exit/marker and actual runtime readiness remain separate; this is not a native Windows compatibility policy.
- **EasyNPC Next inputs and results:** `Utils/wizards/easynpc.py:15–35,37–63,122–162` checks physical Skyrim `Data` and profile list inputs, then exports a small MO2-shaped instance with selected staging, Overwrite, plugin/mod lists and optional `loadorder.txt`. It passes a placeholder `ModOrganizer.exe` path as a tool input, not a running manager. Its launch target is effective Data; it maps `SkyrimSE` versus `SkyrimVR`, but labels both tool-facing exports `Steam`. Prefix `Settings.json` preserves unrelated choices and seeds `Mugshots` only when unset. The fixed export location can retain an old optional `loadorder.txt` if a subsequent profile has none. Output detection scans for `build_info.json` plus `NPC Appearances Merged.esp` and compares size/mtime before and after; registration runs before checking the exit code, with no parse or proof of write ownership (`wizards_qt/easynpc_view.py:334–355`). New rows are initially disabled; existing rows keep state/order (`Utils/mods/install_as_mod.py:89–109`). `easynpc_export_and_merge_belong_to_one_deployed_generation`: include same display name after a profile/root change, missing optional load order after a previous run, stale same-size output, malformed/plugin-only output, a nonzero exit with writes, and cache/output in another profile. Bind the tool-facing export, Data and generated bytes to one run; don't stamp unverified store identity, activate a merge, or mutate an existing output by detection alone.

## Play routing and Skyrim Together

- **Wizard diversion is not executable authorization (M2-L01/M4-Y03):** `Utils/wizards/plugins.py:390–459` maps a finite set of basename candidates against the current title. It prefers ordinary over Discord QAC when both use the same binary name. `gui_qt/app.py:14077–14119,16276–16284` diverts when the current title has a mapped tool and implemented wizard; an authored executable bypasses it. In this set CAO, both translators, BethINI, Wrye Bash and ESLifier have diversion entries; EasyNPC Next, Synthesis and Creation Kit do not. `play_diversion_rechecks_the_exact_selected_role`: same basename in an unrelated or authored location, changed profile, ordinary vs explicit QAC and a missing managed application. No implicit install/setup for a basename collision and no fallback to an unmanaged launch on failed managed preparation.
- **Skyrim Together is a game launch, not a generic tool (M2-L01/M4-Y02/M4-X01/X02):** `Utils/bethesda/skyrim_together.py:5–56` is specific to `skyrim_se`. It prefers a valid effective game-target winner, suppresses physical fallback if a matching staged candidate exists but does not win, and otherwise checks `Data/SkyrimTogetherReborn/SkyrimTogether.exe`. `gui_qt/app.py:14042–14076,14150–14201` offers Launch Together, ordinary Play or Cancel and rechecks game/profile/selector in the reply. Staged-only or other deployed profile can force Deploy before the launch callback. `Utils/executables/launch.py:4068–4125,4449–4454` treats it as a protected launch in the game's prefix with game cwd, ignores a conflicting selected Proton override, and prepares an app-local Windows 10 Wine compatibility entry (`Utils/bethesda/skyrim_together.py:59–74`). Unless overridden in legacy, it passes a logical `SkyrimSE.exe` path to the loader. `skyrim_together_launch_binds_winner_and_actual_game_child`: use vanilla choice, Cancel, loser/disabled candidate, staged-only winner, non-SE lookalike, missing base executable, failed deployment, stale dialog and protected launch refusal. Review the actual runtime/target and do not silently substitute another executable or vanilla view. Linux Wine registry setup is not evidence of a required native Windows registry write.

## Store and compatibility prefix boundaries

- **Same title, distinct deployed files (M4-Y02/M3-B01/M4-D01):** `Games/Bethesda/skyrim_se.py:440–447` declares Steam and GOG AppData and My Games paths; Skyrim VR has a separate path and no GOG sibling (`Games/Bethesda/skyrim_vr.py:148–153`). `Games/Bethesda/bethesda_base.py:476–525,603–629` checks directories in the given prefix and can write both Steam and GOG plugin lists when both exist, otherwise the primary path; existing My Games choices are ordered using GOG-like install markers. `Utils/plugins/__init__.py:132–140,274–312` writes a regular copy, preferring CP1252 with UTF-8 fallback, and sweeps case variants on write/remove. Those behaviors are not ownership proof: a stale sibling directory, stray Galaxy DLL, or differently cased user file does not establish which installation should receive writes. `bethesda_prefix_copy_uses_reviewed_store_and_profile`: Steam only, GOG only, both directories with stale data, VR sibling, writable profile settings and non-CP1252 names. Verify the correct engine-visible file on each route; journal any replacement and preserve unowned variants. Don't copy Linux Wine path conventions to Windows.
- **Tool prefix preparation is a separate effect (M2-L01/M4-Y02/Y03):** `Utils/executables/launch.py:2096–2137,2747–2789,2929–3016` uses the *last deployed* profile for plugin copy (despite the helper name), whereas My Games aliases the normal configured subpath and does not replace an existing destination. These wizard routes may substitute an available runner and can shut down a **prefix-wide** wineserver; that is not authority to stop other tools. For EasyNPC Next, Creation Kit, BethINI, ESP-ESM Translator and Synthesis, distinguish reviewed Data, exported plugin order, prefix-local copies/links and live game-profile changes; a stale destination must not win by its existence. Recheck real process ownership before cleanup. Native Windows must prove an equivalent workflow using its own supported runtime and path bindings.
- **Explicit game-path registration (M4-Y02):** `wizards_qt/bethesda_register_view.py:36–73,85–119` shows a target on opening, but on Write it uses the then-active profile, inspects, and immediately force-writes that revision. `amethyst_backend/game_registry.py:20–65,96–145` binds initialized prefix, runner, game root, scope and observed registry values. `Utils/bethesda/registry.py:48–65,95–132` differentiates x86-only from x64 plus x86 views and does not trust a marker by itself. `Utils/bethesda/registration.py:41–110` rechecks under leases and reports attempted/written views and readback, including partial effects; it does not roll back earlier views. `registry_write_uses_reviewed_profile_and_reports_partial_views`: switch scope after the first preview, change runner, simulate unavailable process scan, fail the second view and require exact readback with no false success; preserve previous authoritative values through recovery on failure. Native Windows install discovery or repair is a separate capability, not generic authority to edit the host registry.
