## Request and job semantics

- Registry declarations include **80** methods requiring `revision`, **62** requiring `confirm`, **100** declaring cancellation and **17** declaring pause. These counts are observations, not Marduk requirements or a substitute for inspecting implementations. Fifteen pause declarations remain once the two third-party manager-plugin download entries are removed; that does not settle which equivalent actions share one Marduk operation.
- `rpc.py:38–81,107–145` treats a request with no ID as a notification, still calls the method, and suppresses its response. Marduk should not allow write/control notifications that cannot produce an acknowledged operation ID. Choose a request envelope and bounded inputs in M4-A02; use schema discovery, structured errors and deliberate batch rules instead of precisely matching the reference's JSON-RPC framing.
- Twelve write/control entries lack `.start`, including installer draft updates/submission, collection manual submission, auth challenge handling, launch stop and job controls. Not everything that writes is a job start, and not every `.start` is a write. Classify allowed effects by the operation, not its name or whether a job object exists.
- `jobs.py:1264–1306` returns terminal state for repeated job controls and calls pausing/resuming callbacks only for supported active jobs. Test that duplicate or stale results don't republish a mod. Separate transient active pause, durable partial-download resume, draft reopening and conflict recovery; the same label does not promise the same persistence.
- Time-consuming reads such as conflict inspection can be cancellable. User approval applies to scoped effects, not to the ability to cancel or observe status. Secrets submitted for authentication are never durable job parameters, error context or log text.
