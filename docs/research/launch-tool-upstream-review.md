## The simpler seam: one launch module, route-specific evidence

Keep discovery, launch review, launch observation and game/tool mutations separate. Game definitions state required path roles, visible outputs and permitted mutations. A platform route consumes a checked executable or launcher entry, intended working directory, structured arguments/environment, bound game/instance/profile and generation, and the resolved runtime/prefix/view. It returns evidence of what was dispatched and what is actually observable or controllable. Core owns leases, recovery, release conditions and effect status; clients cannot assemble fallback command lines. Put native vs launcher-specific details behind the platform seam; don't build a universal launcher automation DSL or reproduce shell handoff scripts as a public interface.

| Route | What upstream establishes | What to prove before claiming support |
|---|---|---|
| Direct Linux | [`pidfd_open`](https://man7.org/linux/man-pages/man2/pidfd_open.2.html) gives stable identity of a **task**, not its descendants. [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html#core-interface-files) exposes recursive population and termination; this does not establish unprivileged delegation or package access. [Rust process docs](https://doc.rust-lang.org/std/process/struct.Command.html) distinguish executable, argv and working directory. | Prefer an OS child handle and verified process identity; use a dedicated delegated job scope only if the package can create and verify it and it solves a demonstrated gap. Exercise a wrapper that exits before a child, a child that changes session, and a same-name unrelated process. Protect roots while users of the view remain possible; never kill by name, guessed PID or process group alone. |
| Direct native Windows | [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) normally include `CreateProcess` descendants, with breakaway, parent-job and `Win32_Process.Create` exceptions. Many completion-port notifications are not guaranteed. `KILL_ON_JOB_CLOSE` changes app-close behavior. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) documents ambiguous executable selection without an explicit application path. | Qualify containment before child execution and verify actual membership/liveness, not notification absence. Test a process already under a job, breakaway/external launcher, manager crash/close and unknown ownership. Do not select kill-on-close without settling intended close behavior. Bind a full executable path; separately qualify Windows batch/command scripts, which aren't native argv targets. |
| Steam and Proton | [Valve Proton](https://github.com/ValveSoftware/Proton/blob/1f089f5610a882c8bfcb4b58a3c86ee88bb4b9f1/README.md#L290-L313) describes Steam-controlled runtime/per-game launch options. [UMU's upstream example](https://github.com/open-wine-components/umu-launcher/blob/e2b203a1fdd2af9f35166f5713cb3f85d72587e2/README.md) shows Steam's wrapper/runtime chain and describes a separate non-Steam path; it does not promise an external process handle for Steam client launches. | Steam store application, non-Steam shortcut, executable and prefix identities are not interchangeable. Compare request accepted vs process observed vs stop authorized; keep Steam/client and package route separate from direct Proton/UMU. No restoring or cleaning a view because a wrapper or submit command exits. Preserve a no-deploy launch where already retained, but never silently use it when a reviewed deployed launch fails. |
| UMU / Wine | [UMU's README](https://github.com/open-wine-components/umu-launcher/blob/e2b203a1fdd2af9f35166f5713cb3f85d72587e2/README.md#L38-L62) documents prefix creation, runtime download, Proton auto-selection and store/game-specific fixes. Its [FAQ](https://github.com/open-wine-components/umu-launcher/wiki/Frequently-asked-questions-(FAQ)) explains that the default Proton verb can wait for an active wineserver and that sharing a prefix has compatibility requirements. [Wine server source](https://gitlab.winehq.org/wine/wine/-/blob/master/server/main.c) distinguishes waiting for the server from managing an individual game process. | Bind prefix, runner version, store and runtime mode before launch; defaults must not silently create a substitute prefix or switch runtime. Report required init/update as part of the reviewed route, not an implicit fallback. When another application shares a prefix, a prefix-wide stop is not a managed game Stop. Busy/unobservable prefix blocks mutation, not read-only reporting. |
| Other launchers and sandboxed builds | [Heroic](https://github.com/Heroic-Games-Launcher/HeroicGamesLauncher/blob/e589e492f2325fceda7d095f33678e468be9b487/README.md) distinguishes stores, runners and packages; [Lutris](https://github.com/lutris/lutris/blob/eace36e97bd0e4d65bcb361b0d785d75433c65e9/README.rst) exposes its own runners. [Bottles](https://github.com/bottlesdevs/Bottles/blob/1b16c736a8adb9c0e7827f82a8290da15407cd9e/README.md) primarily distributes Flatpak; [Faugus](https://github.com/Faugus/faugus-launcher/blob/59e0035e6c51b466bd8ae9d5301653b3cbcf9038/README.md) uses UMU and documents separate Steam interaction permissions. [Flatpak](https://docs.flatpak.org/en/latest/sandbox-permissions.html) recommends portals in preference to blanket filesystem access where possible. | Discovery is read-only, and permission to pick a directory or open a launcher does not establish child access to every runtime/view/output path. Check both directions of any handoff from actual installed packages. Prefer scoped grants; do not expand permissions silently or assume native, sandboxed or external data paths are identical. Record missing permissions and inaccessible installs, not “no games found.” |
| Windows private view | [USVFS upstream](https://github.com/ModOrganizer2/usvfs/blob/57f1ea5e6ad13f7435a7af184748e6c1312c5637/README.md) describes process-selective Windows filesystem hooks and initialization limitations. This is Windows prior art, not the parity baseline. | Retain relocated shadow first. Only study USVFS further for demonstrated canonical-path requirements; qualify architecture, child coverage, early loads, writes and cleanup with independent review and licensing. Never silently launch unvirtualized into public game files if the private route did not bind. |

**Status recommendation:** Separate dispatch, observed process, process ownership, and visibility of the approved generation. An unknown launch observed after a restart is neither “not running” nor authority to signal a process. Hold any affected root/prefix/view lease until safely reconciled. Do not infer game readiness from an app returning zero or from one log line. Scope stop authority to an owned launch; package limitations remain proof gaps, not approved removals. If safe recovery of live launch ownership requires a different close/stop behavior, surface the choice before freezing M2-L01 or the private-view packets.

## Third-party tools: separate acquisition, install, execution and output

- **Different effects, same plan shape.** [xEdit's cleaning guide](https://tes5edit.github.io/docs/7-mod-cleaning-and-error-checking.html) treats QuickAutoClean separately from ordinary xEdit, including an executable-name or argument route. Review any known cleaning intent separately, and treat even an ordinary interactive editor as potentially writable. [Wrye Bash docs](https://wrye-bash.github.io/docs/Wrye%20Bash%20General%20Readme.html) warn about Bashed Patch dependencies and the importance of inactive-plugin ordering. Treat generated game-content plugins as owned outputs, not disposable caches. [DynDOLOD installation](https://dyndolod.info/Installation-Instructions) requires the correct standalone/resources/game variants and advises a separate tool directory; keep DynDOLOD, TexGen and xLODGen variants and output rules separate. [Synthesis](https://github.com/Mutagen-Modding/Synthesis/blob/14cf3fa045e72da68430fbcf7470e9552b0ea8ad/README.md#L13-L17) can execute external patchers: prefix readiness is not permission to install or execute patcher code, build arbitrary projects or promote their output.
- **Version and distribution are action inputs.** [SKSE's release page](https://skse.silverlock.org/) separates Steam/GOG/VR editions and exact supported versions; don't select a loader solely by game title, “latest,” executable filename or naive version ordering. [ReShade](https://reshade.me/) distinguishes ordinary and unsigned full add-on builds and calls out multiplayer limitations; do not silently substitute editions or treat a game starting as compatibility proof. [SMAPI source](https://github.com/Pathoschild/SMAPI/tree/e5b8bf3d601bec0099252c8ee2f54e5571385f1a) has a separate installer and license; inspect the specific release/installation mode before promising parity or bundled distribution. For all tools pin original artifact, expected stable identity and applicable version, source/redistribution terms, target game edition/platform and actual output roots. A checked download is not approved execution.
- **Prefer owned scratch and existing publication.** Run supported tools against an approved disposable input view or explicitly scoped writable targets. Capture designated outputs into an operation-owned stage, inspect bytes/provenance and then publish via the owning archive/library/recovery module. Tools with unavoidable external writes need a per-route rollback/recovery proof, not a broader permission or a promise to undo arbitrary external code. Temporary restore/deploy, prefix init, settings saves and output adoption each need their own durable status. Nonrepeatable effects must not be replayed merely because a worker or launcher lost its response.

## High-risk acceptance before any handoff freezes

1. **`early_wrapper_exit_keeps_view_reserved` (M2-L01/M4-X01/X02):** launcher returns success/ends while inert child still holds the view; new writes and cleanup remain blocked. An unrelated same-name process is never stopped. Recover after manager restart with lost terminal notification; re-observe ownership or surface unresolved state.
2. **`prefix_rebind_or_busy_refuses_setup` (M4-Y02/Y04):** profiles A and B share one prefix. While a process from B owns it, A cannot repair, register, migrate or install dependencies into it. Swap the prefix identity or runner after review: no mutation or silent checkout of a new runtime. Losing observation is not proof of inactivity.
3. **`package_handoff_denial_never_launches_public_fallback` (M2-A01/M4-X01/M4-A03):** launcher exists but lacks access to a synthetic private view or output role. Report the exact failed route; no public fallback, blanket permission grant or misleading running status. Matrix includes native launcher vs packaged launcher and manager, with separately approved real artifact checks.
4. **`tool_exit_is_not_output_commit` (M4-Y03/Y04):** wrapper returns success without expected outputs, or a later capture fails. Keep existing profile/library bytes; report process exit, output verification and any separately committed settings/recovery state distinctly. Repeat with accepted output, stale profile revision and cross-profile capture to prevent adoption into the wrong owner.
5. **`repair_and_migrate_keep_previous_authority` (M3-G02/M4-Y02/Y04):** interrupt a second target mutation or replace a destination/registry file after review. The previously committed config and origins remain authoritative until scoped recovery completes; no broad restore over new external edits and no automatic replay of an unverified installer. Where a third-party tool cannot supply that guarantee on a real route, keep the route gated and ask before narrowing support.
