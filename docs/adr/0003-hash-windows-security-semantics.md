# Hash Windows security semantics, not descriptor bytes

**Status: proposed.** The Windows file fingerprint's security digest covers the owner SID, the group SID and the DACL as an ordered list of effective entries (ACE type, normalised inheritance flags, mask, object GUIDs, SID). Self-relative layout, padding, and descriptor control and provenance flags are excluded; ACE evaluation order is preserved because Windows applies the first matching ACE and reordering overlapping allow/deny entries changes effective access. The copy path (`copy_file`) still applies the source descriptor to the destination.

`SetKernelObjectSecurity` normalises the descriptor it stores, so hashing the raw self-relative bytes made every staged copy and backup differ from its source in a semantically identical DACL; Restore and backup validation would refuse every Windows file. The cost if this is wrong: a descriptor that differs only in stored layout, protection state or inherited-ACE provenance is no longer detected as a mismatch. That difference does not change effective access on the object; if a future guarantee needs protection or inheritance provenance, it must be witnessed explicitly rather than inferred from this digest. Reordered ACEs are deliberately not normalised: the order is part of the grant, and two descriptors with the same entries in a different order hash differently (amended).
