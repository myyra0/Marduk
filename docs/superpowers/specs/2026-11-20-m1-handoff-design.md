# Design: Marduk full-parity audit and implementation handoff

**Status:** Draft for approval. This defines how deep the preparation must go; it is not an executable handoff yet and does not authorize product implementation or workflow changes.

## Intent and scope

Do the expensive reasoning once, up front. A lower-cost orchestrator should be able to run one top-level task in one session, dispatch bounded implementation subtasks, verify their results, and resume from recorded evidence if interrupted. Implementers should not have to discover product requirements or invent APIs, tests, or architecture while building.

Audit the entire base app and plan **M1–M4 in the same preparation pass**. Order execution by dependency and proof, not by the order in which documents are written. Plan downstream work now; where a contract depends on a result we cannot obtain during read-only preparation, isolate the choice behind a named gate and show which packets remain blocked. Keep Rust-first, Tauri 2, Linux and Windows, and recoverable writes as constraints. Do not expand scope into data import, a new plugin system, Reloaded-II support, or a product MCP server.

## What the first working version does

Marduk is a mod manager, not a filesystem. The proposed M1 demo is one representative game, one local archive format, one profile, and a small desktop screen: import two mods that provide the same file, change their priority, deploy the higher-priority file, verify that the game can see it, and restore the original. A narrow CLI exercises the same core operations. If Marduk is interrupted halfway through, reopening it must recover safely; if someone edits a deployed file outside Marduk, Restore must preserve the edit and the original rather than guessing which to keep.

The proposed first deployment method is **copy-based deployment with backups and a recovery journal**. Mods are stored separately and only the winning files are copied into the target game directory. Copies need more space and write access to the target, but avoid the aliasing of hardlinks and the link privileges and game-compatibility questions of symlinks. A virtual filesystem takes a different approach: it presents a merged view to the game without physically placing the winning files in its directory. This is an M1 proposal, not a decision to drop other deployment modes. The audit must check which modes the reference uses and whether a game or workflow requires one. Choose the first game and validate that copying is suitable before locking the M1 contract.

## Approaches

- **Selected: full audit and full-parity planning, with evidence gates.** Specify the whole execution graph, milestone checkpoints and session packets. Use dependency gates to separate choices we can make now from facts that require implementation or platform verification. An open gate blocks its dependent packets, not unrelated work.
- **Superseded: full audit, detailed M1 only.** This avoids early assumptions but leaves later scope and architectural interactions too vague. Retain incremental execution, not incremental planning.

## Preparation work

### 1. Audit behavior and establish coverage

- Use commit `08fe1a481747d64278d75a0e1bb36449d158f584` in the read-only `$LEGACY_PATH` checkout as the parity baseline. If the checkout moves or gains local changes, use the pinned tree as evidence without changing the checkout. Trace desktop, CLI/headless, games and stores, archive/install paths, deploy/restore, profiles and conflicts, integrations, native helpers, bundled functionality, and hidden or partially shipped features. Group repetitive handlers, but account for their variants and exceptions. Distinguish vendored code and scaffolding from user-facing functionality, and record what is shipped, unreleased, or unknown.
- The reference is authoritative for parity. Use MO2 specifically to research Windows behavior where the Linux reference cannot answer the question; do not derive new feature requirements or Linux behavior from MO2. Browse remote repositories with the GitHub MCP.
- Use stable inventory IDs. Each row identifies the behavior and trigger, relevant platform or game variants, evidence, parity disposition, priority/milestone, and how it can be verified. Distinguish observed, documented-only, and unverified behavior. Keep an audit coverage record by entry point or subsystem so a blank area cannot be mistaken for an intentional exclusion. Do not infer coverage from directory names or advertise full parity while retained behavior is unverified.
- Use synthetic input and safe local comparison where useful. Do not modify the reference checkout, real installs, or user files. A runtime comparison that would need a real account, install, or external write is recorded as unverified unless a safe, specifically authorized setup is available.
- Track risky or incomplete retained behavior in the deferred backlog. Count base-app behavior, even if the reference implements it internally as a bundled plugin. Third-party plugin capabilities, the plugin host and compatibility with the existing plugin API are outside the parity target. Assess only the seams needed for future support; do not implement or inventory a third-party ecosystem.

### 2. Resolve architecture decisions across parity

- Define a representative vertical slice from imported mod to applied game files to restored game directory. Choose the initial game, source and archive scope using evidence: it must exercise real discovery or launch assumptions without depending on credentials or broad handler coverage. Synthetic game directories are the default test inputs. The audit decides what the slice demonstrates through the CLI and desktop; both must use the same core operations.
- Settle the contract before parceling out implementation: deployment method and supported filesystems per OS; path and collision semantics; journal, recovery and external-file-edit behavior; locking and concurrent callers; storage and schema; typed operations, events and transport; error and diagnostic boundaries.
- Design M1 for ordinary failure, process interruption, and abrupt loss of power on an explicit initial local filesystem and storage configuration per OS. Test forced process termination at each meaningful transaction boundary on Linux and Windows. For the power-loss model, test lost or reordered writes against the stated persistence barriers, and use abrupt VM power-off on the named configurations where available. Record process, simulated, VM and physical evidence separately: VM shutdown is not proof about physical drives or caches. If evidence on a target is missing, do not call that guarantee verified or quietly lower the requirement; record the gap and bring it to the user before closing the M1 recovery gate.
- When an external edit makes automatic restore unsafe, do not overwrite the edit or discard the recovery copy. Preserve both versions, report the conflict and stop automatic recovery for the affected operation.
- Choose the frontend stack and dependencies on current primary documentation and repository evidence. Prefer existing approaches with a narrow contract and reproducible Linux/Windows verification. Identify license or distribution blockers before committing to reuse. Use narrowly scoped proof work only if reading cannot settle a consequential question, and obtain permission before building a spike.
- Preserve present modular seams. Treat future features as design checks, not APIs to pre-build. The governing docs may be updated to reflect user-approved planning constraints (including routing and escalation); editing the runner, model config or installed skills is separate and not authorized. The core-API rule allows justified extensions for real requirements, not speculative interfaces or broad refactors.
- Make local, reversible decisions and record rationale. Bring the user trade-offs that change supported behavior, release guarantees, or an irreversible boundary; present evidence, viable choices, a recommendation, and what the choice unblocks. Do not ask for routine library or file placement decisions.

### 3. Produce the execution handoff

- Organize M1–M4 as a dependency graph of top-level tasks. Each task has one orchestrator, one session, a clear start state and a verifiable exit. A task can contain several worker subtasks but must be split if it cannot fit a single session under realistic context and verification costs. On interruption, a replacement session resumes from that task's durable record; it does not start the next task or re-decide the design.
- For each top-level task, specify goal, prerequisites, source and decision links, exact acceptance checks, expected evidence, and stop/escalation conditions. Specify witness scenarios that can fail: priority order and collision winners; no writes outside the intended area; failure between journal and filesystem transitions; repeated restore; unmanaged or externally changed files; platform-specific path and filesystem behavior. Map those scenarios to inventory IDs where applicable.
- For each subtask, give the worker the code boundary and files it owns, interfaces and invariants to preserve, tests or fixtures it may and may not edit, commands and expected observations, and an explicit list of work to leave alone. Do not assign two parallel workers overlapping write ownership. If an interface or acceptance test is wrong, the orchestrator escalates it rather than letting a worker change the target to make tests pass.
- The planner decides which scaffold, fixtures, and executable reference tests are worth authoring up front. For high-risk boundaries, provide runnable checks and the minimum seams or test support they need when that is more reliable than asking workers to translate prose. For routine behavior, specify test cases in the briefs. The preparation plan must say which artifacts the planner will author, when they will be run, and who may revise them. Separate any product implementation from this preparation. Keep Linux/Windows execution results distinct from local checks. Missing Windows evidence is pending, not a pass.
- A task is done only when the record links implemented scope, verification commands and outcomes, review findings or resolutions, and the exact point to resume from if the exit checks are incomplete. Higher-cost review is for contracts, transaction safety, audit completeness, and cross-platform risk; prefer mechanical checks over a second model when they can verify the same fact.

### Required depth of execution packets

Each top-level packet must let the orchestrator **dispatch and verify**, not write a new plan. It includes the starting revision or predecessor artifact, required tools and environments, ordered subtasks with dependency links, which can run concurrently, and when to stop. It carries enough context for a fresh session to reconstruct progress by comparing the recorded outputs with the working tree and test results. It does not rely on the orchestrator remembering another session.

Each worker brief must let the implementer **build without inventing behavior**. It includes:

- The concrete public boundary it implements or consumes: input and output shapes, ownership, allowed state transitions, error cases, and which side can cause a write. Identify consumers and the contract source; do not leave the worker to choose interfaces from a list.
- The exact write scope, starting files or fixtures, out-of-scope work, and the handoff artifacts the next worker will consume. If two workers share a contract, settle it once and make both briefs point to it.
- The visible proof of correct behavior: setup, action, expected outcome, and how to tell that the check actually exercises the intended behavior. Where an executable acceptance test is supplied, record its expected pre-implementation failure and protect it from unrelated edits by the implementer.
- An exact local check command and success condition, plus any separate platform, crash, review or manual gate. Missing prerequisites, conflicting evidence, and a needed contract change are stop conditions, not invitations to improvise.

For example, “implement deploy and recovery” is not a usable brief. A recovery packet must identify the selected journal and filesystem transition, the fixture’s starting files, the precise cut point, which bytes and metadata must be present after restart, what may be retried, what must not be touched, and the oracle that checks it. A clean deploy-and-restore test cannot stand in for the interrupted case. The architecture work supplies the actual transition and expected result; this example does not select the journal implementation.

Before the handoff is ready, give a fresh reader one representative high-risk packet and only its linked artifacts. Ask them to identify what to dispatch, which behavior must be preserved, what evidence would justify completion, and when to escalate. Fix gaps in the packet or shared contract rather than relying on a more capable execution model to fill them.

## Records and ownership

`docs/PLAN.md` owns the milestone roadmap. `docs/inventory.md` owns behavior coverage and traceability. `docs/architecture.md` owns the system map and links to approved decisions in `docs/adr/`; the backlogs own exceptions and improvement ideas. The milestone execution plans link those records and own session/task instructions, not duplicate architecture. Keep execution progress separate from both the plans and product feature status; link to observed verification evidence.

Review the existing supervisor, role mapping, installed skills and available tools against a real M1 packet. The prototype assumes a Git repository, an `orchestrator` agent and a particular progress ledger. See the [dispatch gates](../plans/2026-11-20-full-parity.md#before-the-first-behavior-dispatch) for current evidence. Treat those as preflight requirements for unattended execution, not blockers for read-only preparation. Assess whether to keep the supervisor, narrow it to restart/notification, or skip it for the first packet. Recommend changed skills, tools, MCP servers, or a full workflow only if they solve a demonstrated problem better than the existing setup. Keep recommendations separate and do not change the runner, harness, skills, role configuration, hooks or Git setup as part of this work.

Use only the three user-selected models, all at high reasoning effort; [AGENTS.md](../../../AGENTS.md#agent-roles) owns the role split and tier order: Beam for very small bounded work, DeepSeek for orchestration and moderate work, Sol for architecture and risk and as the escalation implementer after two failed cycles on the same task. Do not use an implementer as the sole judge of its own changes or ask an execution model to silently settle an unresolved product or recovery contract. This is a planning constraint and proposed routing, not a change to model configuration.

## Acceptance of the preparation

- The full audit has coverage and evidence, gaps are visible, and retained behavior is traceable to later milestones without treating it as optional.
- Requirements, interfaces and failure/recovery expectations are specific enough to write tests against. Each unresolved decision has an owner, decision criteria and named dependent packets. Any packet depending on an open gate is visibly blocked.
- A fresh reader can pick up a representative packet and identify what to build and how to verify it without reconstructing this conversation. Deferred work and workflow proposals cannot be mistaken for authorized implementation.
