# Marduk M2–M4 Implementation Plan

> **For agentic workers:** Use `subagent-driven-development` for each approved, ready top-level packet. Read the [full plan](2026-11-20-full-parity.md), architecture, and linked inventory witnesses. This catalog establishes scope, ownership, order and acceptance. It does not authorize an open contract or an unapproved implementation.

**Goal:** Build the rest of the base-app workflows after the working core, with no unowned parity requirement.

**Architecture:** Extend proven modules in bounded packets, keeping launch, side-effect recovery, content admission, game rules and provider-specific behavior distinct. Reuse an existing module or helper only at a reviewed seam.

**Tech Stack:** Rust, local SQLite, Tauri 2, typed desktop/CLI/headless DTOs; per-platform dependencies only for named capabilities.

**Spec:** [Full-parity preparation design](../specs/2026-11-20-m1-handoff-design.md), [inventory](../../inventory.md), [architecture](../../architecture.md), [high-risk integration contracts](../../research/integration-contracts.md).

## Global Constraints

- All constraints in the [full plan](2026-11-20-full-parity.md#global-constraints) apply.
- Paths below name intended ownership areas. Freeze the exact files, approved types, fixture bytes, failing/passing commands and witness owners before dispatch. A worker cannot unilaterally select a format, runtime, path policy or supported game range.
- Each ID is one top-level packet and one orchestrator session. Bullets within a row are worker subtasks, sequenced left to right unless the packet ledger marks independent writes. If the named test matrix won't fit, split the packet by provider, game family or environment without merging its ownership with other work.
- Rust checks are future named integration suites, not currently runnable. A packet gate includes actual adapter evidence when the feature is platform specific; browser/mocked providers do not replace native release checks.

## Review Focus

- Two profiles or tools share a physical root while one is recovering: one checked owner, no overlap (M2-D01, M3-X03).
- A provider serves valid bytes for the wrong version, or entitlement changes between preview and apply: refuse incorrect identity (M3-S01/S02, M4-S01/S03).
- A clean view launcher cannot see the merged files, or a tool changes a shared original: fail predictably and keep unrelated views unchanged (M4-X01/X02).
- A handler writes to multiple roots and fails partway: all effects have recoverable ownership, not best-effort cleanup (M4-Y01/Y04).
- A broad smoke passes although desktop-only, package-only or headless outcomes were missed: reconcile exact denominators (M4-A02/A04).

## Packet freeze template

Before naming a later packet `ready`, attach a brief with: predecessor revision; exact files per worker; operation inputs, outputs, IDs, ownership and canonical error behavior; effect and rollback contract; exact fixture/action/oracle and failing/passing check commands; read-only existing test list; eligible parallel writes; review tier; platform and live proof environments; known stops and resume map. If a worker must choose a provider protocol, a game-side effect, or what users can safely lose, that is a missing decision, not freedom to fill in the brief. Track the missing gate on this packet and work an independent ready packet instead.

A brief can live in its packet row if it meets that bar. Link existing contracts and tests rather than writing a second design doc. Pin shared interfaces and observable decisions, not routine internals a test already constrains. For a change affecting multiple clients or adapters, keep one semantic fixture plus any platform-specific proof. Add small UX/reliability improvements to the owning brief only when it can name a distinguishing acceptance check and stays within the approved effect and dependency scope.
