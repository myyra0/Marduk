# Marduk architecture

**Status:** Full-parity design draft. Recorded choices are proposed design unless accepted separately; validation gates are not test results. [Inventory](inventory.md) defines product scope. [Glossary](../GLOSSARY.md) defines terms. [Deployment research](research/deployment.md) records cross-platform evidence. [Plan](PLAN.md) owns the milestones.

## Modules and dependency direction

| Module | Owns | Does not own |
|---|---|---|
| `crates/core` | Stable domain identities, game/profile/model intent, verified library references, priority/conflicts, install and deploy planning, recovery decisions, operation interface and owned adapter traits | OS primitives, HTTP, SQL, Tauri, provider-specific identifiers as domain identity |
| `crates/platform` | Root handles and file identity; bounded filesystem operations; OS launch/session tracking, installation discovery and OS credential storage. Private-view mechanics build here only when selected | Game-specific routing or provider behavior |
| `crates/games` | Game family and title registration, store IDs, game layouts, logical root intents, archive/layout rules, typed tool/launch intents, game-content plugin ordering | Symlink policy, prefix implementation, operating-system filesystem calls |
| `crates/archive` | Readers/writers for enabled formats, archive admission and extraction into a bounded stage, format limits, entry capabilities | Choosing an install profile, direct writes to active game or library roots |
| `crates/storage` | SQL metadata and revisions, content staging/publication, operation journal adapter, indexing and migrations | Deployment decisions, UI formats, implicit writes to installed games |
| `crates/sources` | Provider-specific credentials operations through platform credential adapter, typed identifiers, metadata and download resolution | Publishing mods into the library or editing a game directory |
| `crates/cli`, `app/` | CLI/headless request handling and desktop transport/view state; explicit mapping to the same core operations | Independent engine policies, broad filesystem/shell APIs, direct database access |
| Composition modules in entry points or shared assembly when proven useful | Select adapters, construct registries, wire cancellations and diagnostics | Choosing game behavior based on a global `match` |

Core callers see operation inputs/outputs, not adapter plumbing. The M1 workspace `Op` set is `Setup`, `Status`, `ImportPreview`, `ImportApply`, `Order`, `DeployPreview`, `DeployApply`, `Restore`, `Recover` and `Operation`; later milestones extend it. Exact typed interfaces and wire names belong to the milestone packets. Core owns transaction policy; a real storage adapter and a failure-injecting recording adapter exercise the same seam. Do not make every internal helper a trait. Register new handlers, providers and deploy methods at composition; keep capability and availability independent.

## Domain invariants

- **Game definition, installation, and instance are distinct.** A game definition describes a title/variant; an installation names a discovered or selected physical root and platform/runtime; a managed instance owns profiles and settings. Two instances may share an installation only under one physical-root mutation owner. A changed drive or moved root does not transfer deployment ownership by path text alone.
- **Mod, installed revision, and profile membership are distinct.** Versions are immutable once admitted. A profile revision contains ordered memberships and settings; disabling a member does not uninstall payload, and selecting a profile does not mark it deployed. Linked membership references an immutable revision and retains owner/provenance. Cross-profile and group updates must not silently mutate a previously reviewed plan.
- **File priority is not plugin load order.** Lower in the visible mod list wins an eligible loose-path conflict. A per-file exclusion removes a candidate; a reviewed override must identify an available candidate explicitly. Game/archive load rules remain game-specific. Plan, conflict inspector and file-map export read the same immutable resolved inputs.
- **Game-specific behaviour is declared, not branched.** A title's special rules live in its handler module as named root intents, archive/layout rules, capabilities or typed tool/launch intents; core, platform and other handlers never branch on a game id. Each declared special case names its witness in the [handler ledger](research/game-handler-ledger.md), so it is visible at the declaration site and in review; a per-title condition outside the game handler is a review finding.
- **All filesystem intents have a root role and relative path.** A game handler may target data, install, saves, runtime outputs or a separately approved external root; it does not hand core an unrestricted write path. Platform opens and verifies roots, resolves names with the right volume/game semantics, and rejects unexpected links/reparse points and aliases. Do not lowercase all paths, normalize blindly, or trust a string-prefix check as a write guard.
- **Selections refer to stable identities and revisions.** A plan is bound to its exact game install/root, profile revision, selected mod revisions and input fingerprints. The mutator validates under the root lock, before the first write. Stale plans get a typed error and a fresh preview, not implicit edits.
- **Tool and provider content is untrusted data.** Parse and validate before admit; never execute a script just because an archive included it. Explicit tool acquisition and launch are separate reviewed operations. Credentials stay in the OS keyring; the storage layer holds references or auth state, not secrets.

## Persistence and recovery

**Recommendation:** Single local SQLite database for durable app metadata, revisions, and operation journal; store immutable payload, download partials, staging, backup data and captured files separately. SQLite WAL with `synchronous=FULL` is the starting proposal for durability-critical connections, not a claim that SQLite makes file edits transactional. Journal/schema migrations are forward-versioned and must not discard pending work. Use normal backups independent of SQLite sidecars; never copy a live WAL-managed database file alone as a backup.

See [ADR 0002](adr/0002-journal-external-effects-before-publication.md) for the rationale and the alternatives rejected.

1. **Plan and check ownership.** Determine ordered intents and target-specific capabilities; record explicit requested/effective method. Follow [ADR 0005](adr/0005-one-client-and-one-catalog-per-installation.md) for catalog and installation ownership. The owning journal records pending operations and active generations. Ownership does not stop arbitrary external programs, so publication also needs identity/version checks and conflict handling.
2. **Prepare and persist.** Stage and validate replacement files under the proper root/volume; record pre-images, intended new identity or digest, backup locations, ownership and phase before public mutation. Guarantee backed-up bytes and required metadata are stable before replacement. Never accept a metadata-only placeholder as proof the original can be restored.
3. **Publish and confirm.** Perform the checked replace/create/remove in platform code; only mark a step durable after the required file and namespace persistence steps for the supported target. Keep enough evidence to distinguish “intent persisted but no write” from “write happened but ACK did not.” For an existing target, don't rely on a stat-then-overwrite sequence as an external-edit guard: use a native primitive and sharing policy that protects or retains the actually displaced file, then compare its identity/bytes. If an external writer can race outside the platform guarantee, stop safely or refuse the configuration instead of claiming atomic external-edit detection. No cancellation between an irreversible sub-step and recording its recovery evidence.
4. **Reconcile on restart.** Compare actual old/new/missing/unknown identities against the journal. For an unfinished first deploy, default to rolling back managed changes; for an interrupted restore, continue restoring. Unknown state is not proof of ownership: leave the external file in place, preserve the pre-image and record an actionable `RecoveryConflict` or `TargetUnavailable`. Do not start another mutation on that root until recovery resolves or explicitly releases it. An unrelated root can still operate.
5. **Finalize.** Commit success only after data and explicit state are durable; garbage-collect backups only when no deployed generation, pending operation or user recovery action references them. Never remove unrelated files. Preserve permission/attribute policy for touched originals; if unsupported metadata cannot be preserved, reject or defer the operation rather than claiming an exact restore.

The protocol covers deployment, restore, changes to profile/library user files, external tool output we publish and removal/migration. It cannot make a provider upload or an external tool's independent writes roll back; use preflight and consent, stage controlled outputs, and report remote or out-of-root effects separately. See [deployment research](research/deployment.md) for Windows replacement and sync gaps.

**First proof targets:** local ext4 and Btrfs on Linux x86-64, and native NTFS on Windows x86-64, with recorded disk cache and flush behavior. Btrfs includes library/game subvolume boundaries. The [filesystem matrix](research/filesystem-support.md) distinguishes archive reading, managed storage, game writes, and each deployment method. It also tracks Linux-mounted NTFS and additional filesystems separately. Evidence for one configuration does not cover another.

## Deployment and launch strategy

Shared resolution produces a deterministic generation: logical winners, ownership/conflicts, intended target roles and planning revision. The selected method applies that generation; launch consumes a typed launch intent and a committed deployment/view handle. UI does not need to know which OS mechanism made the files visible.

See [ADR 0001](adr/0001-resolve-deployment-before-placement.md) for how and why the responsibilities are separated.

- **Two deployment strategies, chosen per title and OS.** (A) *Materialised:* copy-based in M1; in M2 add qualified hardlinks and symlinks using isolated mutable sources, not immutable library or recovery bytes. The [link contract](contracts/m2-physical-links.md) owns the capability rules; require approval for each fallback plan before writes. No fallback on ENOSPC, ordinary permission denial or unknown failure. (B) *Private view:* the title reads an overlay and the install is not written, so most conflict, displacement and restore work disappears for that route. Both are first-class users' choices; neither is the default for every game.
- **Private views are per-OS routes, not one portable component.** On Windows evaluate, in order: relocated materialised tree, the existing USVFS injection runtime, then ProjFS or WinFsp — each has different launch, anti-cheat, antivirus and dependency costs, and injection does not cover tools that bypass the hooked process. On Linux evaluate overlayfs or bind mounts inside a launch namespace, then FUSE, and prove Proton/Wine, Steam-launched titles, Flatpak and unprivileged-userns availability before claiming the route. Preserve the clean install on supported routes; report any hybrid root writes separately. Do not couple core to any candidate: a private view registers as a deploy method and a launch route through the existing seams, and no runtime ships before its licence, safe-failure and distribution gates.
- **Generated files:** separate captured outputs from originals and immutable mod payloads. Offer provenance and explicit publish/promote actions. Private view teardown, physical restore, and rollback all preserve recovery evidence. Capture is not license to scan or delete broadly.
- **User selection:** expose physical copy/hardlink/symlink and private game view as separate supported choices. Recommend based on the game, configured paths and runtime. Do not confuse a game-appropriate recommendation with an implementation priority, or make backend choices a requirement users have to understand.
- **Game specialization:** adapters map content and post-deploy work into explicit root intents or separately authorized tool workflows; multi-root operations use recoverable intents. Bethesda plugin order, BG3 mods/settings, RE invalidation, external loaders, and Wabbajack stock game are independent validation cases, not flags on one global game switch.

## Clients, throughput and trust

- **Desktop recommendation:** Tauri 2 + React + TypeScript + Vite; TanStack Virtual for high-cardinality rows keyed by stable ID, native semantics/keyboard controls, CSS tokens for built-in themes. Require both webview smoke tests and a keyboard reorder witness before relying on the UX path; add the 10,000-row synthetic load before high-cardinality profiles. That recommendation is not a layout approval.
- **Typed transport:** all clients share domain operations, but transport types live outside core. Start with mechanically checked desktop DTOs as described in the [M1 client contract](contracts/m1-clients.md). Use structured error codes with safe context, operation IDs and monotonic event sequence, ordered Tauri Channels for live progress and explicit status reads on reconnect. Restrict app commands in the build manifest and scope capabilities to trusted local webviews. No bundled arbitrary shell or broadly scoped frontend filesystem/network capability. [Tauri commands/capabilities](https://v2.tauri.app/security/capabilities/), [Channels](https://v2.tauri.app/develop/calling-frontend/), [TanStack Virtual API](https://tanstack.com/virtual/latest/docs/api/virtualizer).
- **Cross-platform consistency:** Wherever a workflow is offered, share target identity, effect scope, consent, and success/cancel/uncertain/recovery meanings. Allow native differences in file pickers, clipboard representation, URL dispatch, secure storage, codecs and process observation; do not translate a platform limitation into weaker write guarantees, false completion or a silent fallback. Use the same semantic fixture across applicable targets, then prove the real adapter on the installed package. A safe refusal is the right failure result, not proof that an advertised route works. See [cross-platform behavior checks](research/package-route-evidence.md#cross-platform-behavior-checks).
- **Headless:** recommend an explicitly launched local stdio process with version negotiation and bounded typed requests; this recovers automation outcomes without a default listening daemon or preserving the old wire shape. Map sensitive operations to scoped permissions/consent, never infer authority from client type alone.
- **Sources:** bounded downloads, retry with identity checks and declared rate policies, hash verification when available; provider does not apply effects. Collections and lists consume those same reviewed primitives. Use injected fake clocks, providers and staged fixture archives. Network and account smokes never masquerade as contract tests.
- **Performance:** benchmark representative conflict/index sizes, loose vs archives, warm and cold startup, publish/restore and list rendering. Measure before adopting incremental graph complexity. Retain clean cache rebuild and check incremental output against a slow full resolver. Derived caches are not recovery authority.
- **Extensibility:** future plugin host or MCP server is a new caller with explicit permission policy; no code from an untrusted client runs in core. Reloaded-II first evaluates existing runtime integration behind a game/launch seam; no speculative loader API or product MCP in parity. Prefer justified future API extensions over today’s unused abstraction.
