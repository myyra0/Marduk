## Proposed scope and resource contract

- Bind inspection to an admitted source ID, revision and preview generation, including origin for packed members and referenced assets. A closed or superseded inspection cannot redraw, play sound or initiate a capture. Once captured, the immutable image belongs to a separate export review: browsing another NPC in the same live scope cannot replace or cancel that capture. Closing the scope or switching profile invalidates an unclaimed review; after the write is claimed, report its real result and recovery state. Bound aggregate concurrent work as well as per-request input, dimensions/pixels, decoded bytes, archive members, mesh/texture complexity, media duration/work and output. Freeze actual budgets and safe cancellation behavior before dispatch.
- Resolve the final filename, including any `.png` suffix change, before destination and overwrite review. A native dialog's confirmation or a sandbox grant for one filename does not grant access to its sibling. Reopen the picker for the final filename if needed; an expired grant or unsupported safe write path cannot be recovered by writing elsewhere. See [installed platform checks](../research/package-route-evidence.md#cross-platform-behavior-checks).
- Decode admitted local bytes or read handles, not arbitrary renderer paths. A helper, if needed, gets only a narrow typed operation, the selected input and any explicitly admitted companions. No network, unrelated host files, arbitrary commands or unbounded output. Test process/handle cleanup on timeout, close and failure; returned output must itself be admitted and bounded. Read-only inspection may use private scratch, never game/library edits or export to a user location.
- Keep a support row per format, route, OS and packaged decoder. [image-rs decoder limits](https://docs.rs/image/latest/image/struct.Limits.html) distinguish strict dimension checks from non-strict allocation limits: a library setting alone is not proof of a hard memory bound. The [FFmpeg protocol options](https://ffmpeg.org/ffmpeg-protocols.html#Protocol-Options) limit protocols, not which local files a parser may open. [vgmstream](https://vgmstream.org/) is a candidate for the evidenced XWM path; its companion-file support makes an input path alone insufficient confinement. These observations constrain evaluation, not dependency selection.
- Check actual installed decoder capabilities, dependency versions, codec/build options, helper provenance and redistribution per artifact under G-EXT/G-LICENSE. No format is declared retained merely because a dev machine can open it; don't silently drop a supported route because the proposed package can't. A helper or backend choice that changes supported outcomes needs review.
