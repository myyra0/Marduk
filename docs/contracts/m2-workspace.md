# M2 desktop workspace and essential settings

**Status:** Interaction direction selected; packet contracts and fixtures below are drafts. No product or visual-layout approval implied. M2-G01 owns setup and path defaults; M2-P01 owns profile/modlist interactions and preferences; M2-I01 owns local install review; M2-D01/D02 and M2-L01 own deployment/recovery and launch effects. M2-A01 verifies the installed shell. [Inventory](../inventory.md) owns parity, not this screen map.

## Navigation and authority

One game workspace: game and profile selectors, a persistent selected/deployed status, one priority list, and Deploy, Restore and Play in the same view. Separate Library, Profiles and Deployment pages were considered; they hide context during ordinary reorder-and-deploy work. Use focused setup/settings views and short review dialogs instead. This gives M1's fixture screen somewhere to grow without making it design all of M2.

M2 doesn't freeze later screens, custom theme editing, the final palette, remappable shortcuts, locale selection, or provider sign-in. M4-A03 owns appearance and localization, M3-S02 sign-in. Reuse M1's desktop stack and native controls, with shared CSS tokens for `surface`, `text`, `muted`, `border`, `accent`, `focus` and status roles. Use system UI typography; no component kit, per-screen palette, animation layer or global single-letter shortcuts for this slice. Use text with status indicators; never color alone. Reviews return focus to their opener. If a list update removes the focused row, focus the nearest remaining row or the list's empty state.

## Worker fixtures to freeze

- **M2-G01 (`discovery_contract`):** First-route proposal: Skyrim SE through Steam discovery and manual Browse on Linux/Windows. Adapter emits candidates; deduplicate only proven identical physical installs. Store and manual results for one root merge without losing valid launcher information; two roots stay distinct even with the same title. Select Save with valid staging; the initially selected profile has no members or deploy record. Switch request A to B before the A picker/scan returns: A cannot update B or save either. Reopen a persisted game with the game root missing, then with library storage missing; do not recreate either or clear inventory. Reconfiguring existing roots/storage belongs to M3-G02.
- **M2-P01 (`profile_workflow`):** A and B are intentionally distinct IDs with overlapping mod names. Copy A's member order and enabled bits into fresh profile/member identities; editing the copy never edits A's membership. Shared staging may reference the same immutable installed revision, not the same membership. Profile-specific staging uses a distinct owned storage scope; absence blocks operations on that scope and never silently falls back to shared staging. Selection/hide/rename operate by ID, not by display name; selection does not change the active deployment. Review Remove on deployed A, fail Restore, and verify A and its referenced bytes still exist. Removal cannot reclaim any payload referenced by another profile or recovery record.
- **M2-P01 (`profile_workflow`, list):** Start with enabled `A`, disabled `B`, a locked separator, then `C` at highest priority. Save a sorted, filtered view, close and reopen. Verify the original priority order and separator lock survive. Try crossing the separator, reordering while filtered, and applying a stale edit from a second client; all leave the priority unchanged. Clear the filter and reorder within a section using the keyboard; verify exact member IDs and last committed deployment unchanged. Batch enable/remove applies only to reviewed selected IDs; hidden checked rows must be disclosed before Apply. Name/notes/flags changes and create-empty do not deploy.
- **M2-D01/L01 (close):** With two eligible active deployments, configure Restore on Close. A running managed process blocks restoration of its root; failed Restore leaves the exact pending/conflict state and does not display a clean shutdown. Closing after a separately acknowledged exit-without-restore keeps journal and lease evidence. Restart or update entry points must use the same guard, not treat saving settings as permission to close.
- **M2-A01 (`desktop_essentials`):** On each installed OS build, start with no games, complete setup, import and explicitly replace a mod, create/switch profile, reorder, deploy, Restore and reopen. Use the same golden file/identity assertions as CLI. Exercise an unavailable configured root and a canceled or late picker. Separately run a seeded 10,000-row list: scroll, filter, select and keyboard reorder by ID; verify the rendered rows stay bounded by the viewport plus overscan. Record cold/warm launch-to-workspace and filter timings with machine/build details for [M3-A01](../superpowers/plans/2026-11-20-m2-m4-parity-packets.md#m3--major-integrations-and-data-workflows), not a timing SLA from one machine.

Before freezing G01/P01, name the concrete settings keys, files and types, and bind these witnesses to the M1 scaffold and revision model. Prove which profile-specific storage and physical launch routes are available; read/write availability is separate from process visibility. Automatic deploy remains a retained conditional outcome: freeze its reviewed opt-in scope and revalidation rules with the relevant effect owners before enabling it. Do not infer authorization from a saved checkbox, a different profile or an unavailable requested method.
