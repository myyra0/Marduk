## Secure storage decision

The pinned Nexus OAuth, mod.io and LoversLab routes include non-keyring credential storage behavior. Marduk's agreed baseline is OS keyring and no plaintext persistence or logging; compatibility with old credential files is not required. Missing keyring on a supported target is a behavior decision, not just an error branch. Before closing the affected routes, report which packaged environments actually lack the service and compare (a) secure-store provisioning and clear no-persistence/session-or-browser handling where viable, (b) a separately reviewed protected fallback with a defined key source, lock and recovery model. Ask before giving up established cross-session sign-in or introducing a new secret storage scheme. Do not require the worker to choose. Locked/denied/unavailable must not trigger silent downgrade or revive revoked credentials.

Use inert per-user credentials to check store/read/clear and relaunch from the actual installed package in separate login sessions. Record the Windows persistence class and each Linux package's service availability, unlock path and allowed access. Neither an unlocked development session nor browser sign-in proves persistent in-app sign-in. See the [platform references](../research/provider-upstream-review.md#shared-checks-that-remain-open).
